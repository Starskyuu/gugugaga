# 四船协同搜救软件操作指南

版本：1.0  
适用对象：中心基站塔、4 艘搜救小船、模拟场地正上方视觉识别系统  
适用条件：待救目标位置固定，视觉系统持续提供船位、船艏朝向和目标位置

## 1. 系统怎么工作

数据链路如下：

```text
顶视相机 + YOLO/标记识别
          │ UDP：船/目标的水面坐标
          ▼
中心基站：目标锁定 → 精确任务分配 → A* 路径规划
          │ Wi-Fi + TCP：航点、目标编号、急停
          ▼
4 艘小船：航点跟踪 → 电机指令 → 状态/救援完成回传
```

程序针对 10 个固定目标使用两层规划：先用动态规划为每条船、每个目标子集求最短访问顺序，再把所有目标精确分给 4 艘船，使最后一艘船的预计完成时间尽量短；有障碍时，每一段实际航路由 A* 计算。10 个目标规模下可以快速求解。

## 2. 文件说明

- `base_station.py`：基站主程序，接收视觉数据、规划并管理船端连接。
- `boat_agent.py`：每艘船运行一份，默认不驱动硬件。
- `rescue_core.py`：A*、路径简化和四船任务分配算法。
- `protocol.py`：基站与船端共用的 JSON/TCP 通信协议。
- `vision_sender_example.py`：视觉系统接入示例和样例数据。
- `web_visualizer.py`：浏览器实时二维态势图和人工操作按钮。
- `start_local_demo.py`：一台电脑上的完整干运行演示。
- `dynamic_simulator.py`：四艘虚拟船的动态运动和视觉坐标仿真。
- `configs/base_station.json`：场地、障碍、船速和通信参数。
- `configs/boat_1.json` 至 `boat_4.json`：四条船各自的参数。
- `firmware/esp32_boat_controller/`：ESP32 双推进器串口控制示例。
- `tests/`：算法自动测试。

## 3. 硬件和网络建议

推荐使用一个独立的 2.4 GHz Wi-Fi 路由器/AP，所有设备只接入这个局域网。示例地址如下：

| 设备 | 建议固定地址 | 运行内容 |
|---|---:|---|
| 中心基站计算机 | `192.168.50.10` | `base_station.py` |
| 视觉计算机 | `192.168.50.20` | YOLO、坐标标定、UDP 发送适配器 |
| 船 1–4 的树莓派/小型计算机 | `192.168.50.101`–`.104` | `boat_agent.py` |
| ESP32 | USB 串口连接本船计算机 | 电机 PWM 与硬件超时停机 |

防火墙需允许基站入站 TCP `9000` 和 UDP `9100`。AP 不需要连接互联网。正式演示前应实测全场 RSSI、丢包、延迟和重连时间。

## 4. 第一次在普通电脑上验证

要求 Python 3.10 或更高版本。核心仿真不需要安装第三方包。

1. 打开 PowerShell，进入本目录：

   ```powershell
   cd "F:\gugugaga\09 software"
   ```

2. 运行算法测试：

   ```powershell
   python -m unittest discover -s tests -v
   ```

   应看到 4 项测试全部显示 `ok`。

3. 启动完整干运行演示：

   ```powershell
   python start_local_demo.py
   ```

   程序会自动选择未占用的网络端口，并在默认浏览器打开“**四船协同搜救实时态势**”页面。终端会打印实际地址，例如 `Dynamic demo is running at http://127.0.0.1:53124`；没有自动打开时请复制终端显示的地址，而不是固定使用旧的 `8080` 地址。大约 1–2 秒后应显示“在线 4/4、已救 0/10”，四艘虚拟船会沿彩色路线移动，抵达目标后红点变绿并重新规划。按 `Ctrl+C` 结束。该模式不会访问 GPIO、串口或实体电机。

   如果误打开旧的 `http://127.0.0.1:8080` 页面，可能仍会看到“在线 0/4、已救 0/0”。请以本次终端打印的新地址为准。程序自动换用空闲端口，因此即使旧进程暂未关闭，也不会再把新模拟数据发送给旧基站。

### 4.1 二维界面怎么看

- 蓝色水域中的三角形代表搜救船，尖端表示船头方向。
- 红色圆点代表尚未救援的固定目标，绿色带勾圆点代表已完成目标。
- 深灰矩形是障碍物，外围橙色虚线区域是加入船宽和定位误差后的安全禁区。
- 蓝、绿、橙、紫实线分别是四艘船当前的 A* 路线。
- 右侧“船队状态”显示连接、位置和最后心跳时间。
- 右侧“路线分配”显示每条船的救援顺序、路程和预计时间。
- “重新规划”保留当前目标并重新计算；“重置任务”清除目标锁定和完成记录；“全船急停”立即向在线船只发送停机命令。

页面以约 6–7 Hz 刷新。本地演示使用 `dynamic_simulator.py` 产生连续变化的船位；接入真实系统后，船只图标改为跟随顶视视觉坐标。同一 Wi-Fi 下的手机或平板也可访问 `http://基站IP:8080` 查看。

## 5. 配置中心基站

把整个 `09 software` 目录复制到基站计算机。编辑 `configs/base_station.json`：

```json
"map": {
  "width_m": 6.0,
  "height_m": 4.0,
  "resolution_m": 0.1,
  "safety_margin_m": 0.15,
  "obstacles": [[2.8, 1.4, 3.2, 2.6]]
}
```

- `width_m`、`height_m`：标定后水面作业区的实际宽高。
- `resolution_m`：A* 栅格边长。模型场地通常可从 `0.05–0.10 m` 试起。
- `safety_margin_m`：障碍膨胀距离，应覆盖半个船宽、定位误差和制动余量。
- `obstacles`：矩形障碍列表，每项依次为 `[x_min, y_min, x_max, y_max]`，单位米。没有障碍时写 `[]`。
- `speed_mps`：各船经实测得到的安全巡航速度。
- `rescue_service_s`：船到达一个目标后模拟救援所需时间。

启动带二维界面的基站：

```powershell
python base_station.py --config configs/base_station.json --visualize --open-browser
```

如果只需要命令行日志，可以去掉 `--visualize --open-browser`。树莓派无桌面运行时保留 `--visualize`、去掉 `--open-browser`，再从同一网络的电脑访问 `http://树莓派IP:8080`。看到 `Base station ready` 后保持程序运行；按 `Ctrl+C` 会先向在线船只发送急停，再退出。

## 6. 接入顶视视觉系统

视觉程序必须先完成像素坐标到水面米制坐标的单应性变换，并保持 4 艘船 ID 稳定。建议在船顶使用不同编号的 ArUco/AprilTag；仅靠外观检测容易发生 ID 互换。

向基站 `192.168.50.10:9100` 周期性发送 UTF-8 JSON UDP 数据：

```json
{
  "type": "VISION_FRAME",
  "timestamp": 1788320000.123,
  "boats": [
    {"id": "boat_1", "x": 0.40, "y": 0.40, "heading": 0.0, "confidence": 0.98}
  ],
  "victims": [
    {"id": "person_1", "x": 1.10, "y": 0.90, "confidence": 0.97}
  ]
}
```

约定：

- `x/y` 单位为米，原点和方向必须与基站地图一致。
- `heading` 单位为弧度，`0` 表示朝 +X，逆时针为正，范围可用 `[-π, π]`。
- `timestamp` 必须是 Unix 秒，视觉计算机和基站应同步系统时间。
- 四艘船 ID 必须严格使用 `boat_1` 至 `boat_4`。
- 固定目标第一次被可靠识别后，基站锁定其坐标；单帧抖动不会改变目标位置。
- 默认过滤置信度低于 `0.60` 或时间差超过 `1 s` 的数据。

最直接的接法是把 `vision_sender_example.py` 中的 `SAMPLE_BOATS`/`SAMPLE_VICTIMS` 替换成 YOLO + 单应性变换的结果，并在每帧调用 `send_frame()`。先用示例验证网络：

```powershell
python vision_sender_example.py --host 192.168.50.10 --port 9100 --repeat
```

## 7. 配置四艘小船

每条船需要能运行 Python 的树莓派/小型计算机；若船上只有 ESP32，不能直接运行 `boat_agent.py`，需增加树莓派，或将 TCP/导航逻辑移植到 ESP32。

1. 把这些文件复制到每条船：`boat_agent.py`、`protocol.py`、对应的 `configs/boat_N.json`。
2. 确认每条船配置中的 `boat_id` 唯一，且 `base_station_host` 是基站固定 IP。
3. 先保留以下安全配置：

   ```json
   "motor_driver": {"type": "console"}
   ```

4. 在船上运行，例如船 1：

   ```powershell
   python boat_agent.py --config configs/boat_1.json --dry-run
   ```

5. 基站日志应出现 `boat_1 connected`；船端应出现 `Accepted path`。

四条船分别运行 `boat_1.json`、`boat_2.json`、`boat_3.json`、`boat_4.json`。不要复制后忘记修改 `boat_id`。

## 8. 连接 ESP32 和电机驱动

> 安全要求：首次上电必须拆下螺旋桨或把船架空；准备实体断电开关；严禁在人员手边带桨调参。

1. 使用 Arduino IDE 打开 `firmware/esp32_boat_controller/esp32_boat_controller.ino`。
2. 安装 ArduinoJson 7 库。
3. 按实际 TB6612/L298N/其他驱动板修改 `LEFT_PWM`、`LEFT_DIR`、`RIGHT_PWM`、`RIGHT_DIR` 和 `ENABLE_PIN`。驱动板必须与 ESP32 共地；电机电源不要直接取自 ESP32。
4. 上传固件并确认串口波特率 `115200`。
5. 船端安装串口库：

   ```powershell
   python -m pip install pyserial
   ```

6. 查找串口号。Windows 可在设备管理器查看 `COM3` 等；Linux 常见 `/dev/ttyUSB0` 或 `/dev/ttyACM0`。
7. 修改对应船配置：

   ```json
   "motor_driver": {
     "type": "serial",
     "port": "COM3",
     "baudrate": 115200
   }
   ```

8. 保持螺旋桨拆除，启动船端并发送一条短路线，核对左右、正反方向。方向相反时优先交换电机线或修改固件方向，不要通过增大控制增益掩盖接线错误。

ESP32 固件自带 `500 ms` 命令超时：上位机卡死或 USB 断开后会关闭电机。船端还有 `server_timeout_s`，默认 3 秒收不到基站消息就停止推进。

## 9. 控制参数调整

在 `configs/boat_N.json` 中逐步调整：

- `cruise_output`：归一化推进输出，初次下水建议 `0.20–0.30`。
- `heading_gain`：转向修正强度。左右摆动就减小；转弯迟钝再小幅增加。
- `waypoint_tolerance_m`：认为到达普通航点的半径，应略大于视觉定位抖动。
- `rescue_radius_m`：判定到达目标的半径，应结合船首救援机构尺寸。
- `pose_max_age_s`：视觉位姿可使用的最长时间；超过后船端立即停机。

调参顺序是单船直线、单船转弯、单船绕障、两船、最后四船。每一步都保留人工断电能力。

## 10. 开机和关机顺序

开机：

1. 清空水域并检查电池、电机、急停和障碍坐标。
2. 启动 Wi-Fi AP、基站和视觉系统，确认坐标方向正确。
3. 四条船先以干运行连接，检查规划结果。
4. 将船放入各自视觉起点，逐条启用串口电机模式。
5. 低速开始任务；观察基站路径与实际运动是否一致。

关机：

1. 先在基站按 `Ctrl+C`，等待急停下发。
2. 确认所有推进器停止。
3. 关闭船端程序和船上主电源。
4. 最后关闭视觉系统、基站和 AP。

## 11. 常见故障

| 现象 | 重点检查 | 处理 |
|---|---|---|
| 基站收不到视觉数据 | UDP 9100、防火墙、目标 IP、系统时间 | 用示例发送器测试；校准两台电脑时间 |
| 船连接不上 | TCP 9000、基站 IP、同一 Wi-Fi、船 ID | `ping` 基站；核对配置和防火墙 |
| `planning_failed` | 起点/终点落入障碍、无路可达、坐标越界 | 查看地图尺寸、障碍和安全膨胀值 |
| 船始终不动 | 没有 `POSE_UPDATE`、位姿过期、仍是 console 模式 | 先确认视觉持续发送 heading 和时间戳 |
| 船方向相反 | 电机接线或左右定义错误 | 拆桨后校正接线/固件引脚 |
| 船来回摆动 | heading 噪声或增益太高 | 检查船头标记，降低 `heading_gain`/速度 |
| 多船可能相撞 | 当前版本只做静态障碍全局路径 | 加大间隔，设置单向区或分批放行；正式载人设备不得直接使用本原型 |

## 12. 当前版本边界

该程序适合课程模型和受控场地原型，不是经过认证的真实水上救援控制系统。它已经包含固定目标精确分配、A* 绕障、版本化路径、心跳、失联停机和 ESP32 硬件超时，但尚未实现严格的多船“时间-空间预约”避碰、真实电池管理、GNSS/IMU 融合、加密认证和独立硬件急停。四船联动演示时应通过低速、足够安全间距、人工监控和实体断电开关弥补这些边界。

## 13. 交互式搜救小游戏

在本目录运行：

```powershell
python rescue_game.py
```

也可以双击 `启动搜救小游戏.bat`。程序会自动选择空闲端口并打开浏览器。

游戏场地按实际模型尺寸等比例绘制：60 × 60 cm；中央基站位于正中央，尺寸 22 × 15 cm；每艘船长 7 cm、宽 5 cm；基站左侧和右侧各停靠两艘，船头朝外。开始任务时四艘船先驶出基站，再前往各自目标。

操作方法：

1. 在水域点击或拖动，逐个加入小人；切换“点击删除”可移除目标。
2. 若需大量目标，在数量框输入 `1–1000`，点击“随机布置”。
3. 在“选择算法”中选择均衡最近邻、分区最近邻或精确四船动态规划。
4. 点击“开始搜救”，系统分配四船任务并生成绕开基站安全区的路线。
5. 使用“暂停/继续”和 `1×–30×` 速度调节观察过程。
6. “船只归位”保留小人并重新开始；“清空小人”删除全部目标。

算法选择说明：均衡最近邻适合 1–1000 人，兼顾距离和四船负载；分区最近邻适合 1–1000 人，计算最快但可能不够均衡；精确四船动态规划适合 1–12 人，使用 Held–Karp 和四船子集划分追求最小化最忙船航程。三种任务分配算法均使用矩形可见图绕开中央基站安全区。
